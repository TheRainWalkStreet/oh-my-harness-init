# 垃圾回收模式

熵管理 —— 周期性扫描，用于发现漂移，而不仅仅是风格违规。

## 安全规则

- GC 脚本**必须是只读的**：扫描和报告，永远不自动修复或删除
- 任何自动修复能力**必须**要求显式的 `--fix` 标志和用户确认
- 定时 CI 运行（cron）**必须**是仅报告模式（退出码 + 创建 Issue）
- GC 脚本**禁止**修改源文件、删除文件或修改 git 历史
- GC 工作流权限：`contents: read`、`issues: write` —— 不能更多

## 两大类别

### 风格扫描（基础，噪音较多）
- 原始 console/print 语句（应使用 logger）
- 默认导出（JS/TS —— 应使用命名导出）
- 大文件（>300 行警告，>500 行报错）
- TODO/FIXME/HACK 注释
- 缺少类型注解
- 未使用的 import

### 熵扫描（高价值，OpenAI 真正关注的）

| 扫描项           | 实现方式             | 说明                                                                 |
|------------------|----------------------|----------------------------------------------------------------------|
| **文档-代码漂移** | 自动（git log）      | docs/ 的描述是否匹配当前代码行为？见下方"知识新鲜度"检查            |
| **架构违规**      | 自动（边界测试）     | 是否有新的 import 违反了 LAYERS.md？                                 |
| **依赖审计**      | 自动（工具扫描）     | 是否存在循环或不必要的依赖？                                         |
| **质量棘轮**      | 自动（计数比对）     | KNOWN_VIOLATIONS 是否增加了？                                        |
| **模式偏离**      | **人工审查**         | 代码是否不符合 golden-principles/？此项**无法可靠地自动化**，建议列入 PR Review Checklist，而非纳入 GC 脚本 |

**优先进行熵扫描，而非风格扫描。** 风格是 Linter 的职责。

## 知识新鲜度检查

检查 `docs/` 是否在 `src/` 发生变更后超过 **30 天**未更新：

```bash
# 检查 src/ 在最近 30 天内是否有提交
SRC_RECENT=$(git log --since="30 days ago" --oneline -- src/ | wc -l)

# 检查 docs/ 在最近 30 天内是否有提交
DOCS_RECENT=$(git log --since="30 days ago" --oneline -- docs/ | wc -l)

if [ "$SRC_RECENT" -gt 0 ] && [ "$DOCS_RECENT" -eq 0 ]; then
  echo "WARNING: src/ 在最近 30 天内有 $SRC_RECENT 次提交，但 docs/ 无任何更新。文档可能已过时。"
  exit 1
fi
```

> **阈值说明：** 默认 30 天。活跃迭代的项目可调低至 14 天；文档密集型项目可调高至 60 天。在 GC 脚本中将阈值定义为常量，便于团队自定义。

## GC 执行器

单一命令运行所有检查：
```bash
npm run gc        # 或
python scripts/gc_run_all.py  # 或
make gc
```

每个脚本：扫描 → 发现违规 → 报告 `文件:行号` → 退出码 0（无问题）/ 1（有问题）。

## 定时执行

GitHub Actions cron `0 9 * * 1`（每周一 UTC 9:00）。
结果以 `garbage-collection` 标签发布为 GitHub Issue（或对应 CI 平台的 Issue 系统）。

## 如何处理 GC 结果

GC 扫描不会自动修复任何问题。发现问题后，按以下方式处理：

| 扫描类型     | 处理方式                                            |
|--------------|-----------------------------------------------------|
| 架构违规     | 创建专项 Issue，分配 `architecture` 标签，列入下一迭代 |
| 文档漂移     | 创建 PR 更新过时的 docs/ 文件，保持与代码同步       |
| 风格问题     | 批量修复 PR（可用 `--fix` 模式自动修复风格类问题）  |
| 质量棘轮增加 | 阻断 CI，必须在合并前修复                           |

## 现有仓库的迁移策略

1. **建立基线：** 运行所有扫描，记录当前数量
2. **仅警告阶段：** 新违规仅警告，不触发 CI 失败
3. **棘轮阶段：** 锁定基线数量，数量增加时 CI 失败
4. **收敛：** 通过有针对性的清理 PR 逐步降低基线
