# coding.md 模板

用于生成 `docs/standards/coding.md`。最终项目默认只生成一个代码规范文件。

```markdown
# 代码规范

## 规范来源

- 项目现有工具：{ESLint/Ruff/Checkstyle/etc}
- 项目现有约定：{README/docs/配置}
- 本文件补充：{工具无法覆盖的 review 标准}

## 通用工程规范

- 命名表达业务含义，避免模糊缩写。
- 函数、组件、类只承担一个清晰职责。
- 业务规则放在业务层，不放在 UI、Controller、Handler 或模板层。
- 外部系统调用集中封装，避免散落在业务代码中。
- 错误必须保留可诊断上下文，但不得泄露敏感信息。
- 输入边界必须显式校验，输出边界必须明确类型或结构。

## 命名规范

{按项目语言和现有风格生成。}

## 代码组织与分层规范

{结合 ARCHITECTURE.md 的真实层级生成。}

## 注释与文档规范

{何时写注释、何时更新文档。}

## 错误处理与日志规范

{异常、错误返回、日志字段、敏感信息规则。}

## 测试规范

{单元测试、集成测试、关键路径、mock/stub 规则。}

## 命令覆盖规范

- 新增源码目录或业务模块后，必须确认测试、lint、format、build 命令覆盖新代码。
- 如果命令只覆盖单个入口文件或部分源码，必须在 `docs/ENGINEERING.md` 中标出覆盖风险。
- v1.3.0 不自动改造项目命令；需要改命令时，应由用户明确发起开发任务。
- Agent 不得因为存在 `npm test`、`make test`、`pytest` 等命令就假设覆盖范围完整。

## 安全编码规范

{输入校验、认证授权、密钥、SQL/ORM、XSS/CSRF/CORS 等。}

## 技术栈专项规范

{按检测到的语言和框架插入专项规则。}

## Agent 编码禁止事项

- 不绕过现有 lint/format/typecheck。
- 不凭空新增架构层或公共工具。
- 不复制外部规范全文。
- 不提交真实密钥、账号、内部地址或漏洞细节。
- 不把格式化、重构、功能和文档大面积混在一个变更中。
```

## 生成规则

- 先读取 `references/coding-standards-profiles.md`。
- 先尊重项目工具，再补充人工 review 标准。
- 只生成当前技术栈相关章节。
