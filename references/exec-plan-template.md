# 执行计划标准（docs/exec-plans/）

## 文件命名规范

```
docs/exec-plans/active/{YYYY-MM-DD}-{feature-slug}.md
```

例如：`2026-04-22-user-auth-refactor.md`。按日期前缀命名便于按时间顺序排列，`feature-slug` 使用 kebab-case（全小写，连字符分隔）。

---

两个互补的来源：
- **OpenAI Harness 文章** —— `docs/exec-plans/` 目录，有生命周期（active → completed）
- **OpenAI Cookbook PLANS.md** —— 单文件执行计划格式（自包含的活文档）

适用于复杂功能或重大重构。小型变更不需要。

## 目录结构（来自 Harness 文章）

```
docs/exec-plans/
├── active/                # 进行中的计划
│   └── {功能名称}.md      # 每个功能/重构一个计划
├── completed/             # 已完成的计划，附回顾总结
│   └── {功能名称}.md      # 保留以供下游 Agent 了解历史决策
└── tech-debt-tracker.md   # 已知技术债，已排优先级（可选）
```

活跃计划完成后移入 `completed/`。下游 Agent 可以在没有人工上下文的情况下推断之前的决策。

## 单文件替代方案

对于较简单的项目，仓库根目录的单个 `PLANS.md` 或 `.agent/PLANS.md` 也可以。有多个并行功能的仓库推荐使用目录结构。

## 核心要求

- **完全自包含** —— 新人无需额外知识即可实现。自包含的范围包括：① 实现背景与目的；② 相关 ADR 和决策；③ 依赖服务的通用描述（不含凭证）；④ 如何运行和验证。不需要包含：如何搭建本机开发环境（链接到 `docs/guides/setup.md`）。
- **活文档** —— 随着进展、意外情况、决策不断更新
- **可重启** —— 仅凭执行计划即可恢复工作，无需其他状态

## 必需章节

```markdown
# <简短的行动导向描述>

本执行计划是一份活文档。

## 目的 / 全局视角
用户获得什么，如何验证它正常工作。

## 预估工时
{预计总工时，例如：4-6 小时。超过 2 小时的任务才需要 ExecPlan。}

## 进度
- [x] (YYYY-MM-DD HH:MMZ) 已完成步骤
- [ ] 待完成步骤

## 意外情况与发现
- 观察：...
  证据：...

## 决策日志
- 决策：...
  理由：...
  日期/作者：...

## 成果与回顾
结果总结、差距和经验教训。

## 上下文与定位
当前状态，假设读者对此一无所知。

## 工作计划
编辑和添加的顺序，具体指明文件名。

## 具体步骤
精确命令及其工作目录，包含预期输出。

## 验收与验证
如何启动/使用系统。可观测的行为，而非内部属性。

## 幂等性与恢复
步骤是否可重复？回滚路径是什么？

## 制品与备注
关键输出示例，保持简洁。

## 接口与依赖
要使用的库、模块、函数签名。
```

## 适用场景

- 需要修改多个文件/模块的复杂功能
- 触及架构的重大重构
- 多小时的实现任务

## 不适用场景

- Bug 修复
- 小型功能添加
- 配置变更
