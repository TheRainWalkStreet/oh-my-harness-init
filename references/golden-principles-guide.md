# 黄金原则编写指南

在 `docs/golden-principles/` 目录下创建文档，每个 30-60 行，包含 DO/DON'T 代码示例和**执行方式说明**。

> **核心要求：** 每条黄金原则**必须**说明由哪个工具机械执行。没有执行工具的规范只是 Markdown，不是约束。

## 编写方法

1. **先阅读实际代码库的模式。** 发现，不要猜测。
2. 每个文件只涵盖**一个**主题。
3. 先陈述规则，再展示 DO/DON'T 代码示例，最后写明执行方式。
4. 保持 30-60 行实质内容（不含空行和注释行）—— 如果更长，请拆分主题。

## 将学习持续升级为约束

> 这是 harness 工程长期健康运行的核心循环，来自 OpenAI 实践和社区经验：**"如果审查者重复说了同样的话两次，就把它编码进工具。"**

当一个问题反复出现时，按照以下阶梯逐级升级约束强度：

```
发现问题
  │
  ├─ 第 1 次出现 ──→ 在 docs/golden-principles/ 中澄清规则
  │
  ├─ 第 2 次出现 ──→ 添加测试覆盖（boundary test / unit test）
  │
  ├─ 第 3 次重复 ──→ 添加静态约束（Lint 规则 / 结构检查）
  │
  └─ 持续发生    ──→ 脚本/自动化（GC 任务 / pre-commit hook）
```

**每一级的含义：**

| 级别 | 措施 | 触发时机 | 效果 |
|------|------|----------|------|
| Docs | 在 golden-principles/ 写明规则 + 示例 | 首次发现 | 告知 Agent 和人类正确做法 |
| Tests | 加测试覆盖该失败模式 | 第二次出现 | 防止回归，CI 检测 |
| Lint/结构 | 加静态规则，报错含修复指引 | 第三次重复 | 编译时/提交时阻断 |
| 自动化 | 编入 GC 脚本或 hook，定期扫描修复 | 持续发生 | 存量问题也被持续清理 |

**实践规则：**
- 不要在第一次就上 Lint 规则 —— 先写文档，确认规则是合理的
- 不要在问题消失后维持过重的约束 —— 定期在 GC 时回顾是否可以移除
- 每次升级都更新 `docs/golden-principles/` 对应文件的"执行方式"章节

## 候选主题筛选策略

阶段 0 发现可能揭示 10+ 个值得写的主题。优先级：

1. **优先写"当前违规最多的 top 3"** —— 从实际 import 错误、Lint 报错中找频率最高的问题
2. **其次写"后果最严重的"** —— 安全相关、数据损坏风险的规则
3. **最后写"新成员最容易踩的"** —— 命名、目录结构约定

**目标数量：** 必需 2-3 个，推荐上限 6 个。超过 6 个通常意味着主题可以合并。

## 常见候选文件

根据技术栈选择合适的文件（不需要全部创建）：

### 通用（所有技术栈）

| 文件                  | 主题                               | 适用场景   |
|-----------------------|------------------------------------|------------|
| `IMPORTS.md`          | 路径别名、import 排序、禁止深层相对路径 | 始终需要 |
| `NAMING.md`           | 文件命名、导出规范                 | 始终需要   |
| `ERROR_HANDLING.md`   | 错误处理与上报                     | 始终需要   |
| `TESTING.md`          | 测试什么、测试模式                 | 如果有测试 |
| `LOGGING.md`          | 日志规范                           | 如果有自定义日志 |

### 前端专项（JS/TS）

| 文件                  | 主题                 | 适用场景   |
|-----------------------|----------------------|------------|
| `DATA_FETCHING.md`    | 数据获取与缓存       | React/Vue/Next.js |
| `STATE_MANAGEMENT.md` | 状态管理规范         | 有全局状态时 |
| `COMPONENT_DESIGN.md` | 组件拆分与接口设计   | 大型前端项目 |

### 后端/Java 专项

| 文件                      | 主题                             | 适用场景             |
|---------------------------|----------------------------------|----------------------|
| `DEPENDENCY_INJECTION.md` | Bean 注入规范，禁止字段注入      | Spring Boot          |
| `TRANSACTION.md`          | 事务边界规范，@Transactional 用法 | 有数据库操作时       |
| `DTO_MAPPING.md`          | DTO 与领域对象转换规范           | 分层架构项目         |
| `EXCEPTION_HANDLING.md`   | 全局异常处理与自定义异常层级     | REST API 项目        |

### Python 专项

| 文件                  | 主题                 | 适用场景   |
|-----------------------|----------------------|------------|
| `TYPE_HINTS.md`       | 类型注解规范         | 有 mypy 时 |
| `ASYNC_PATTERNS.md`   | 异步编程模式         | FastAPI 项目 |

## 模板

~~~markdown
# {主题}

## 规则
{一句话规则陈述}

## 应该这样做（DO）

```{语言}
// 好：{为什么这样是正确的}
{代码示例}
```

## 不应该这样做（DON'T）

```{语言}
// 不好：{为什么这样是错误的}
{代码示例}
```

## 执行方式

由 `{工具名}` 的 `{规则名}` 自动执行。
配置位置：`{配置文件路径}`
违规报错：`{报错信息示例，包含修复指引}`

## 例外情况
{规则不适用的场景，如有；若无则省略此节}
~~~
