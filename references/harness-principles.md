# Harness 原则

## 核心思想

harness 的目标不是生成大量文档，而是让项目把关键知识沉淀为 Agent 能稳定读取、维护和验证的仓库资产。

## 设计原则

1. 入口短，细节分层
   - `AGENTS.md` 是目录，控制在 80-140 行。
   - 复杂规则进入 `ARCHITECTURE.md` 和 `docs/`。

2. 事实优先
   - 只写能从仓库验证的信息。
   - 不确定内容标记为 `待确认`。
   - 不根据通用模板编造业务、命令、目录或依赖关系。

3. 企业级不是大而全
   - 默认结构要克制。
   - Extended 文档必须由项目事实触发。
   - 空壳文档会降低 Agent 信号质量，不要生成。

4. 规范要可执行
   - 开发规范、提交规范和架构规则必须能指导实际改动。
   - 无法工具化检查的规范，也要写清楚人工 review 标准。

5. 计划和技术债是一等工件
   - 复杂任务进入 `docs/exec-plans/active/`。
   - 完成后归档到 `docs/exec-plans/completed/`。
   - 长期技术债进入 `docs/exec-plans/tech-debt.md`。

## 不做什么

- 不替空项目设计技术栈。
- 不修改 CI、lint、pre-commit、边界测试或其它自动化门禁。
- 不复制外部规范全文。
- 不生成 `.gitkeep`。
